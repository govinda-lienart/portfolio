<Abstract>
Stage 1 converts raw aquarium video into a structured, frame-level MySQL dataset in
two steps: each video is registered once, along with its metadata, in a MySQL `videos` table, then
sampled at one frame per second into a `frames` table foreign-keyed back to
it, so each frame stays traceable to the video it came from. The result is a reproducible ingestion layer: consistent
1 FPS sampling, lossless PNG frames on disk, and structured metadata across
two relational tables in a Dockerised MySQL database, forming the foundation
the annotation and training stages build on.
</Abstract>

## Introduction

Annotation, which entails drawing bounding boxes for object detection, needs still, addressable images, not a
continuously playing video. Therefore the video is extracted and stored as frames, and bounding boxes are drawn on those frames.
Each frame must be findable again by frame number later, when its annotation is associated to it and stored.
Stage 1 builds that addressable image set: it establishes the first two of AquaMind's four MySQL tables (`videos`
and `frames`) and a script that samples at a standard one-frame-per-second rate, spaced widely enough to capture
varied fish positions, which Stage 2's annotation work and Stage 3's YOLO training dataset are built on.

## Aim

Build a database where a video's frames can live: indexed by frame number and
timestamp, so Stage 2's annotation work has something stable to label.

### 1. Choosing a recording format

Initial recordings using iPhone 14 (iOS 26) in HEVC (H.265) format introduced
frame-level colour inconsistencies when processed with OpenCV, resulting in
degraded colour fidelity during extraction.

This issue comes from how inter-frame compression works: modern codecs store
occasional full frames and encode only the pixel differences between them to
reduce file size. When OpenCV's software decoder processes an HEVC-encoded file,
colour reconstruction can break down during this decoding process, producing
washed-out frames.

<Figure src={hevcFaded} alt="Faded frame colours due to HEVC codec" caption="Faded colours extracted from an HEVC-encoded MOV file." width={700} />

To ensure deterministic frame decoding, the recording format on iPhone was
switched to H.264 ("Most Compatible" mode). Although this increased storage size,
it significantly improved frame consistency and colour stability during
extraction.

<Figure src={h264Settings} alt="iPhone camera settings switched to Most Compatible mode" caption="Correct colour reproduction after switching to H.264." width={700} />

Recordings were standardised at 60 FPS to increase temporal resolution, enabling
finer capture of fast behavioural events such as feeding strikes.

### 2. Setting up the database

A MySQL 8.4 instance runs inside a Docker container, isolated from any local
database installation, with port 3306 exposed so both the Python scripts and
MySQL Workbench can connect to it.

Stage 1 creates two relational tables: `videos`, one row per registered
recording, written by <a href="https://github.com/govinda-lienart/AquaMind/blob/main/scripts/sync_videos.py" target="_blank" rel="noopener noreferrer"><code>sync_videos.py</code></a>, and `frames`, one row per extracted
frame, written by <a href="https://github.com/govinda-lienart/AquaMind/blob/main/scripts/extract_frames.py" target="_blank" rel="noopener noreferrer"><code>extract_frames.py</code></a> and foreign-keyed back to its parent
video. Splitting registration from extraction this way means a video's
metadata (species, tank dimensions, filming date) is recorded once, not
repeated on every one of its frame rows.

### 3. Registering videos

<a href="https://github.com/govinda-lienart/AquaMind/blob/main/scripts/sync_videos.py" target="_blank" rel="noopener noreferrer"><code>sync_videos.py</code></a> reads one row per video from `video_metadata.xlsx`:
species, morph, tank dimensions, activity, fish count, and filming date, the
experimental metadata that isn't in the video file itself. `fps` and
`resolution` are not taken from the spreadsheet; they're read directly from
the video with OpenCV, so they can't drift out of sync with the actual file.

The insert is an upsert keyed on `file_path` (`INSERT ... ON DUPLICATE KEY
UPDATE`), so re-running the script is safe: an already-registered video gets
its metadata refreshed instead of duplicated, and `register_video()` reports
back which of the two happened.

### 4. Extracting frames

**Design overview.** <a href="https://github.com/govinda-lienart/AquaMind/blob/main/scripts/extract_frames.py" target="_blank" rel="noopener noreferrer"><code>extract_frames.py</code></a> reads video files sequentially using OpenCV and
extracts frames at a fixed rate of one frame per second. Each extracted frame is
saved both as an image file and as a structured record in a MySQL database.

**Frame-rate normalisation.** The frame rate of each video is retrieved directly
using OpenCV. However, iPhone recordings give a frame rate of `59.94` FPS instead
of a clean `60` FPS due to underlying NTSC video-encoding standards. If used
directly, this small discrepancy causes `frame_count % fps == 0` to select frames
inconsistently. The FPS value is wrapped in `round()` to normalise it to the
nearest integer before being used in the sampling logic.

**Sampling strategy.** Frames are selected using the expression
`frame_count % fps == 0`, which ensures that exactly one frame per second is
extracted. The video is read frame by frame using OpenCV, which returns a boolean
`ret` and the `frame` image data on each call. When `ret` becomes `False`, the
video has reached its end and the loop terminates.

**Frame storage.** Each selected frame is saved as a PNG image to preserve full
image quality without compression loss. This matters because the dataset is
intended for future annotation and machine-learning tasks where pixel-level
accuracy counts. For every frame the system records its index and computes its
timestamp in seconds relative to the start of the video using `frame_count / fps`.

## Results

Ingestion correctness was verified by querying `frames` directly: sequential
frame indexing aligned with the sampling rate, consistent 1-second timestamp
increments, valid file-path references to the stored PNG frames, and correct
separation between different extraction runs in the filesystem.

## Discussion

Stage 1 establishes a reproducible ingestion pipeline in two steps: <a href="https://github.com/govinda-lienart/AquaMind/blob/main/scripts/sync_videos.py" target="_blank" rel="noopener noreferrer"><code>sync_videos.py</code></a>
registers each video once, and <a href="https://github.com/govinda-lienart/AquaMind/blob/main/scripts/extract_frames.py" target="_blank" rel="noopener noreferrer"><code>extract_frames.py</code></a> samples it at a temporally
consistent 1 FPS. Reliable H.264 decoding, lossless PNG frames on disk, and
metadata split across the `videos` and `frames` MySQL tables together form the
foundational dataset layer for subsequent annotation, labelling and model
training.

The 1 FPS sampling contract fixed here is specific to this stage's own
script, not to the `frames` table as a whole: a later hard-negative-mining
step feeds tracker-flagged crossing frames back into the same table on its
own, event-triggered sampling (Stage 2 covers that). The tracker itself needs
full temporal resolution for its own matching, so [Stage 4](/aquamind/stages/04-tracker/)
reads the raw video directly instead of going through this table at all.
