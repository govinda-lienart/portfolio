<Abstract>
Stage 2 turns the frame dataset from Stage 1 into a supervised-learning dataset
by hand-labelling every visible fish with a bounding box in Label Studio,
exporting the result in YOLO format, and parsing each box into a relational
`annotations` table keyed back to its source frame. 366 bounding boxes were
labelled across 61 frames. This is the labelled-data layer the detector is
trained on in Stage 3.
</Abstract>

## Introduction

Stage 2 implements the annotation layer of the AquaMind pipeline, where each
extracted frame from Stage 1 is manually labelled by drawing bounding boxes around
every visible fish. This turns the raw frame dataset into a supervised-learning
dataset by adding object-level labels to each image.

To store these labels in a structured way, an `annotations` table is created in
MySQL. Each annotation represents a single bounding box for one fish and is linked
back to its frame via a foreign key (`frame_id`). The labels are also exported in
YOLO format for model training.

```text
Video → Frames → Annotations → Database → AI model
```

## Aim

Produce a labelled dataset a detector can train on: every visible fish boxed by
hand, exported in a training-ready format (YOLO), and stored as relational rows
that trace back to their source frame — so annotation coverage, provenance and
later re-labelling are all queryable rather than living only in flat files.

### Environment setup

The same `aquamind` Conda environment from Stage 1 is used. No additional Python
packages are required; `mysql-connector-python`, `os` and `datetime` are already
installed.

### Labelling infrastructure

Label Studio is used for manual annotation and is launched as a Docker container.
No local installation is required beyond Docker Desktop being active. It runs as a
single container using the `heartexlabs/label-studio:latest` image. Port 8080 is
mapped to the host, and a volume mount gives Label Studio persistent storage: all
annotation data is written to the local `mydata` folder on the host rather than
inside the container, so the work survives a container restart.

```bash
docker run -it -p 8080:8080 -v $(pwd)/mydata:/label-studio/data heartexlabs/label-studio:latest
```

### Annotation

Inside Label Studio, a new project named *AquaMind* is created. The labelling
interface is configured under Settings → Labelling Interface: the Computer Vision
category, the *Object Detection with Bounding Boxes* template, and a single label
class `danio_rerio_golden`. All extracted JPG frames from Stage 1 are imported as
individual tasks.

Each frame is opened individually and a bounding box is drawn around every visible
fish, one box per fish.

### YOLO export

Once all frames are annotated, the project is exported in *YOLO with Images*
format. The archive contains:

```text
classes.txt       # label names (label = "danio_rerio_golden")
images/           # frame images
labels/           # one .txt file per image with bounding-box coordinates
notes.json        # metadata
```

Each `.txt` file corresponds to one frame and contains one line per bounding box:

```text
class_id  x_center  y_center  width  height
```

All five values are normalised between 0 and 1 relative to the image dimensions,
making the format resolution-independent. For example:

```text
0  0.242  0.668  0.103  0.113
```

This line represents one fish: class 0 (`danio_rerio_golden`).

### Database schema

Before storing annotations, the `annotations` table is created with a foreign key
linking each record back to its frame in the `frames` table.

```sql
CREATE TABLE annotations (
  id         INT AUTO_INCREMENT PRIMARY KEY,  -- unique row identifier
  frame_id   INT,                             -- foreign key to frames table
  FOREIGN KEY (frame_id) REFERENCES frames(id),
  class_id   INT,                             -- YOLO class index
  label      VARCHAR(255),                    -- human-readable label name
  x_center   FLOAT,                           -- normalised x center
  y_center   FLOAT,                           -- normalised y center
  width      FLOAT,                           -- normalised box width
  height     FLOAT,                           -- normalised box height
  created_at TIMESTAMP                        -- system time of insertion
);
```

### Batch provenance: `annotation_sets`

Later in the project, once frames came from more than one source, each labelling batch got its own
row in an `annotation_sets` table, and `annotations` gained an `annotation_set_id` foreign key next
to `frame_id`. One row records where a batch came from and how it was labelled: the video
(`video_id`), the `frame_source` (`regular`, `crossing_event` or `ghosting_event`), the sampling
parameters (`sample_rate`, `start_seconds`, `end_seconds`, `frames_extracted`, plus `iou_threshold`
and `dedup_window` for crossing-event batches), and the Label Studio project (`ls_project_name`,
`ls_project_id`, `ls_downloaded_at` and the task-id range).

`store_annotations.py` fills it from two sidecar files: `extraction_params.yaml`, written next to the
frames by the extraction script (Stage 1), and `download_params.yaml`, written next to the export by
`download_labelstudio.py`. Every box can then answer which video, which sampling and which Label
Studio download it came from, and Stage 3 can build a training set by choosing annotation sets
rather than loose files.

### Annotation-storage pipeline

**Design overview.** <a href="https://github.com/govinda-lienart/AquaMind/blob/main/scripts/store_annotations.py" target="_blank" rel="noopener noreferrer"><code>store_annotations.py</code></a> iterates over every `.txt` file in the exported
`labels/` folder. For each file the frame number is parsed from the filename,
used to retrieve the `frame_id` from the `frames` table, and each bounding box is
inserted as a record into `annotations`.

**Filename parsing and frame-ID lookup.** Label Studio exports annotation files
with a hash prefix followed by the frame name (e.g. `e6d83681-frame_360.txt`). The
frame number is parsed from the filename and used to query the `frames` table:

```sql
SELECT id FROM frames WHERE frame_number = %s
```

`cursor.fetchone()[0]` returns the `frame_id`, used as the foreign key when
inserting into `annotations`. This lookup ensures every annotation is linked to the
correct source frame regardless of file ordering.

**Reading and casting bounding-box values.** Each line represents one bounding
box. The five whitespace-separated values are read and cast (`class_id` to `int`,
the four coordinates to `float`) so they are stored with the correct types in
MySQL.

**Inserting into MySQL.**

```sql
INSERT INTO annotations (frame_id, class_id, label, x_center, y_center, width, height, created_at)
VALUES (%s, %s, %s, %s, %s, %s, %s, %s)
```

The `label` field is set to `danio_rerio_golden` and `created_at` is generated at
insertion time with `datetime.datetime.now()`. Once all files are processed,
`conn.commit()` saves the rows and `conn.close()` frees the connection.

### Auto-labeling — model-assisted labeling

*Once Stage 3 has a trained `@champion` detector, a small Label Studio ML
backend (a server implementing `predict()`, loading the model via
`model_registry.py`'s `load_yolo()` — the same resolver `tracker.py` uses)
serves it back into Label Studio, so newly imported frames arrive pre-boxed and
only need correcting rather than drawn from scratch. This is a forward
reference: the model this section uses doesn't exist until Stage 3 trains it,
so this labeling step only switches on partway through the project, once a
first detector is registered. It's a labeling-speed tool, not a decision about
which frames are worth labeling — that selection is
[Stage 5](/portfolio/aquamind/stages/05-detector-improvement/)'s
`extract_crossing_frames.py` and `extract_ghost_frames.py`, mining tracker
failures to send back here.*

## Results

Correctness is verified by querying the `annotations` table directly:

```sql
SELECT * FROM annotations;
```

Expected properties: one record per bounding box, `frame_id` values matching the
`frames` table, normalised coordinates between 0 and 1, and consistent `label` /
`class_id` values across all records.

### Auto-labeling coverage

*Fraction of frames where the champion model's predictions needed no correction
vs minor/major correction, and any measured speedup vs the fully manual baseline
above. Any failure modes (e.g. suppressed detections during crossings — the same
weak point Stage 4 and Stage 6 document).*

## Discussion

Stage 2 establishes a reproducible annotation pipeline that links every extracted
frame to a structured set of bounding-box records in MySQL: Label Studio as a
lightweight annotation environment, **366 labelled fish instances across 61
frames** in YOLO format, each box parsed and stored as a relational record linked
to its source frame, all inside the Dockerised MySQL environment. This forms the
labelled dataset layer for downstream model training.

*Auto-labeling likely helps most on routine, single-fish frames and least on
crossing/occlusion frames — which is exactly what Stage 5's failure-driven
frame selection sends for manual review anyway. Together, model-assisted
labeling (this section) and failure-driven frame selection form the manual
improvement loop written up in [Stage 5](/portfolio/aquamind/stages/05-detector-improvement/).*
